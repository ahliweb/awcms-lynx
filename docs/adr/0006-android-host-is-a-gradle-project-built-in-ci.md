# ADR-0006 — The Android host is a Gradle project that CI builds, lints and unit-tests

- **Status:** Proposed (decision recorded with the pull request that closes issue #24; becomes Accepted when that pull request is merged by a maintainer)
- **Date:** 21 November 2026
- **Decision maker:** ahliweb maintainers (review of the pull request)
- **Related:** ADR-0002, ADR-0003, ADR-0004; `hosts/android/README.md`; `hosts/README.md` STATUS; issue #24

## Context

Until now `hosts/android` held reference Kotlin sources that no CI job compiled. A downstream build spike (2026-11-21) compiled them against Lynx 4.1.0 and found one real error: `LynxLoadMeta.Builder` setters return `void` in 4.1.0, so the chained call in `AwcmsLynxHost.createView` does not compile. Reference sources that are not built drift silently; this was the first drift found. The spike also fixed a set of toolchain versions that work together (below). The template needs a buildable Android host so that a derived product starts from a green build, and so that the host contract (ADR-0003) is replayed on the JVM and not only on the web and desktop hosts.

## Decision

**D1. A minimal Gradle project (Kotlin DSL) lives in `hosts/android`.** Root files `settings.gradle.kts`, `build.gradle.kts`, `gradle.properties`, the Gradle wrapper (`gradlew`, `gradlew.bat`, `gradle-wrapper.jar` generated by the official Gradle 8.13 distribution, `distributionSha256Sum` and `validateDistributionUrl=true` in the properties), and one `app` module (`id.ahliweb.awcms.lynx`, a placeholder application id) with `App`, `MainActivity`, manifest, backup and data-extraction rules.

**D2. Versions are pinned and were verified together:** Lynx 4.1.0, PrimJS 4.1.1, Android Gradle Plugin 8.9.1, Gradle 8.13, Kotlin 2.0.21, Fresco 2.3.0, OkHttp 4.9.0; JDK 21 runs the build and the code targets Java 17; `compileSdk`/`targetSdk` 36, `minSdk` 24.

**D3. The existing reference sources stay the compiled sources.** The files `hosts/android/*.kt` are staged by a `Sync` task into a generated source root; `app` adds only the Application, the Activity and resources. The bundle `apps/mobile/dist/main.lynx.bundle` is copied into the APK assets by a Gradle task that fails with an explicit message when the bundle is missing. The `LynxLoadMeta` call is fixed to use a builder variable.

**D4. CI gets a separate `android` job** in `.github/workflows/ci.yml`: Bun builds the bundle, JDK 21 (Temurin) and the runner image's Android SDK build it, `gradle/actions/wrapper-validation` rejects an unofficial wrapper jar, then `./gradlew assembleDebug lintDebug testDebugUnitTest` runs. The new job's third-party actions are pinned by commit SHA.

**D5. The host contract is replayed on the JVM.** A parameterised JUnit 4 test runs every case of `hosts/contract-test-vectors.json` against `HostBridgeDispatcher` (one test per case) plus two fault tests for the cases the vectors list as not covered (`STORAGE_UNAVAILABLE`, `HOST_ERROR`). The real Keystore store and the Lynx module adapter are not covered; they need a device.

**D6. Devtool is a `debugImplementation` dependency only,** so the release APK carries no devtool classes. Registering the devtool service remains the documented, product-side step (`hosts/android/README.md` §3). R8 stays off in release until the Lynx keep block is added and a release build is run on a device.

## Options compared

| Criterion | A. Gradle project in `hosts/android` + CI job (chosen) | B. Keep reference sources, build only downstream | C. Gradle project, built inside the existing `check` job |
| --- | --- | --- | --- |
| Pros and cons | Drift found in CI, a derived product starts green; adds files and a toolchain to maintain | No maintenance here; the bug above would stay and every product re-discovers it | Single job; Android toolchain failures block the JS checks and the whole job gets slower |
| Security | Wrapper checksum and validation action guard the supply chain; actions pinned by SHA; no secrets; debug keystore only | No new surface here; no review of Android dependencies | Same as A |
| Performance | Job runs in parallel with `check`; Gradle cache on main | None | CI wall time is the sum |
| Maintainability | Version bumps (Lynx, AGP, Kotlin) are one PR with a green signal | Versions drift between products | Same as A, noisier failures |
| Scalability | The same pattern can host an iOS or Harmony job later | Does not scale to more hosts | Poorly: one job accumulates toolchains |
| Accessibility | No change to the UI; lint runs Android accessibility checks on the host shell | None | Same as A |
| SEO | Not applicable | Not applicable | Not applicable |
| UI/UX | Host shell only (launches the same bundle) | None | Same as A |
| Compatibility | Verified combination of versions; Lynx 4.1.0 matches the JS packages' docs | Unverified against any Lynx version | Same as A |
| Operational complexity | One extra job, one wrapper jar in the repository | None here, more downstream | One job with two runtimes plus JDK and SDK |
| Long term | Honest status ("compiled and unit-tested in CI"); device runs remain a product PoC | Status stays "reference only" | Same as A with coupling |

## Consequences

- `hosts/android` becomes buildable: `bun run build:mobile` then `./gradlew assembleDebug lintDebug testDebugUnitTest` in that directory (Android SDK required; set `ANDROID_HOME` or `local.properties`).
- The status for Android moves from "reference sources" to "builds, lints and passes the 74 contract vectors in JUnit in CI". No device run, no instrumented test, no release build, no signing and no R8 run is claimed.
- Renaming the application id and the namespace is a derived product's first step.
- A new Lynx, AGP, Gradle or Kotlin version is a deliberate change of D2 and re-runs the job; the `VERIFY` list in `hosts/android/README.md` records what the build did and did not confirm.
- Upgrading the wrapper replaces `gradle-wrapper.jar` and `distributionSha256Sum` together; the wrapper-validation step must stay green.
